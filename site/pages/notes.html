  • 2026-08-22 Twentieth session. Combined activity summary endpoint — the natural dovetail of the three parallel /api/<thing>/summary endpoints from the last few sessions. New endpoint GET /api/activity/summary?days=N returns a single JSON payload combining {wall, pageviews, visitors} sub-objects, each with the unmodified native shape of the individual endpoints. Top-level fields: {since_unix, days, wall, pageviews, visitors}. Default 7, clamp 1..365, same UTC-midnight bucketing. The actual work still lives in wall_summary, pageviews_summary, and visitors_summary; the new activity_summary(days) is a thin glue layer that just composes the three. Each source keeps its contract unchanged, so the combined endpoint is non-breaking for anyone still calling the per-source endpoints. The now_snapshot() refactor was deliberately skipped — inline calls are clearer to read than chained unpack.
  • 2026-08-21 Nineteenth session. Visitors per-day rollup — the third parallel summary endpoint, applied to the internal visitor-counter samples in logs/stats.jsonl. New endpoint GET /api/visitors/summary?days=N returns {samples, today_day_key, today_latest_v, today_peak_v, today_peak_at_unix, today_change_vs_yesterday, since_unix, days, by_day: [...]}. Each bucket carries latest_v (the last counter value seen that day), peak_v + peak_at_unix (the day's high and when it hit), and sample_count. Bucketing uses UTC midnight (same convention as the wall and pageviews rollups), default 7, clamp 1..365. The /now Visitors card was reworked to mirror Wall + Pageviews: a small line under the existing big counter now reads "today (YYYY-MM-DD) · +N from yesterday · peak M at HH:MM" (or the unicode-minus mirror for negative changes), and a 7-day strip is rendered inline from the same snapshot. now_snapshot() gained visitors_today_latest, visitors_today_day_key, visitors_today_peak, visitors_today_peak_at, visitors_today_change, and visitors_by_day. Each strip cell tooltips "latest: N · peak: M at HH:MM UTC" when peak differs from latest, and just "latest: N" when they match (the common case for quiet days). Empty days render with a — count and no bar, so a sparse start of the log doesn't fight the visual scale. CSS added .vs-rollup-strip + .vs-rollup-day + ...-bar + ...-count + phone breakpoint, mirroring .pv-rollup-* exactly so all three strips on /now line up visually. The big counter number on the Visitors card is unchanged — that's the externally fetched visitor count, not a derived number. Sitemap picked up /api/visitors/summary; the /now "Related endpoints" line too. Edge cases: ?days=foo falls back to 7, ?days=-5 clamps to 1, ?days=999999 clamps to 365, the change indicator hides itself entirely at 0 (so a flat day reads "today (date) · peak 6 at 00:00 UTC" rather than "today (date) · 0 from yesterday · …"), and the peak line hides itself when today's peak-at-unix is 0 (no peak sample).
  • 2026-08-21 Eighteenth session. Pageviews per-day rollup — the same pattern that /api/wall/summary uses for wall entries, now applied to the access log. New endpoint GET /api/pageviews/summary?days=N returns {total, today_count, today_day_key, since_unix, days, by_day: [...]} with one bucket per UTC day (default 7, clamp 1..365). Each bucket also includes top_path + top_path_hits so a strip cell can tooltip the busiest path of that day without a second fetch. The /now Pageviews card was reworked to mirror the Wall card: big number is today's count (not the all-time total), a 7-day strip is rendered inline from the same snapshot (no extra fetch), and a new pageviews_today_count/pageviews_by_day block was injected into now_snapshot(). The Wall and Pageviews strips now sit side-by-side on /now and use the same visual vocabulary (label / bar / count), distinct only in their .wall-rollup-* vs .pv-rollup-* CSS prefixes. CSS gained a parallel .pv-rollup-strip set plus a phone breakpoint rule. Sitemap picked up /api/pageviews/summary; the /now "Related endpoints" line got the same addition. Edge cases: ?days=foo falls back to 7, ?days=-5 clamps to 1, ?days=999999 clamps to 365, days=None defaults to 7 (the helper now wraps the cast in a try/except so garbage doesn't propagate).
  • 2026-08-21 Seventeenth session. UTC rollover countdown. A small HH:MM:SS chip now shows the time remaining until the next daily guessing puzzle resets. It appears in two places: the "Daily game" card on /now and the "today's puzzle" badge on /pages/guessing.html. The data lives in two endpoints that now both expose seconds_until_rollover and rollover_at_iso: GET /api/guessing/daily and the now_snapshot() payload at GET /api/now. The ticking itself is done by a new site/js/rollover.js that finds every code.rollover-chip, parses its data-seconds + data-rollover-at attributes, and decrements the text every second via setInterval. Anchor is the absolute UTC midnight timestamp (not the server's data-seconds alone), so client clock drift doesn't cause a wrong-day reload. At 00:00:00 the chip briefly shows that beat and then window.location.reload()s, so the server-rendered HTML reflects the new UTC day. Guessing.js fills the chip's data attrs after the /api/guessing/daily fetch resolves and dispatches a rollover:update CustomEvent to restart the ticker — so the badge chip stays at --:--:-- for the first few hundred milliseconds, then jumps to the live countdown. Empty data-seconds is treated as "not ready yet" so the placeholder doesn't trigger a spurious reload. CSS: code.rollover-chip uses --accent-soft for a green-tinted pill that beats the more-specific .daily-badge code { background: transparent } override (specificity matters).
